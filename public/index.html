미니 샌드박스 mini-redis · mini-rdbms

같은 PC에서 실행 중인 두 서버를 직접 호출하고, 작은 삽입·조회 실험을 해 볼 수 있습니다. 모든 요청은 이 페이지의 로컬 프록시(127.0.0.1)를 거쳐 전달됩니다.

Redis·SQL 결과, 요청 기록, HTTP 실험·C 벤치마크·버킷 구조 비교 결과와 내보내기 대상을 화면에서 지웁니다. 저장된 파일·주소·입력값·서버 상태는 그대로 둡니다.

실험 대기 중입니다.

측정 방법과 해석 시 주의할 점
  • RDBMS는 실험마다 새 프로세스와 새 데이터 디렉터리(mini-sandbox/data/runs/<실험ID>/)로 실행합니다. 엔진에 DELETE가 없고 ID가 자동 증가하므로, 같은 조건을 반복하려면 빈 테이블에서 시작해야 하기 때문입니다.
  • 각 시스템에 같은 값을 같은 건수만큼 보냅니다. 요청은 한 번에 하나씩 순서대로 보내며, 반복할 때마다 시스템 순서를 바꿉니다.
  • 준비(인스턴스 시작, 상태·모드 확인, 키가 비어 있는지 확인), 검증(전체 조회, CSV 줄 수), 정리 시간은 측정 구간에서 제외하고 따로 표시합니다.
  • 구간 시간은 해당 구간 첫 요청 시작부터 마지막 응답까지의 브라우저 시간입니다. 성공 처리량은 성공 건수 ÷ 구간 시간입니다. 실패·불일치는 성공으로 세지 않습니다.
  • 시간 지표의 정확한 시작·종료 지점과 포함 범위는 아래 “측정 경계와 해석” 표를 보세요. 통계는 성공 요청만 표본으로 쓰며, 표본 수와 누락 수를 함께 표시합니다. 서버가 보내지 않은 시간은 추정하지 않고 “서버에서 제공되지 않음”으로 표시합니다.
  • 실험이 끝나면 원시 요청 기록(요청 순서, 상태, 각 시간), 설정, 실행 순서, 저장·flush 조건, 실행 환경을 mini-sandbox/data/results/에 JSON으로 저장합니다. “JSON 내보내기”로 내려받을 수도 있습니다.
  • 저장 방식이 다릅니다. mini-redis는 프로세스 메모리에만 보관하며 종료하면 사라집니다. mini-rdbms는 INSERT마다 CSV에 덧붙이고 fflush합니다. fsync·WAL은 없어 전원 장애 내구성은 보장하지 않습니다. 따라서 삽입 속도 차이를 같은 조건의 DBMS 우열로 해석하지 마세요.
  • scan 모드도 삽입 시 B+ 트리를 유지합니다. 조회만 CSV 전체 탐색을 합니다. 작은 건수에서는 차이가 잡음보다 작을 수 있습니다.
  • 두 서버 모두 단일 스레드입니다. 긴 요청이 처리되는 동안 다른 요청은 기다립니다. 실험 중 다른 탭이나 도구로 같은 서버를 호출하면 결과가 달라집니다.

5. C 내부 벤치마크 (HTTP 없이 C 프로세스 안에서 반복 측정)

짧은 조회를 HTTP로 하나씩 재면 통신·이벤트 루프 비용이 결과를 지배합니다. 여기서는 페이지가 설정만 보내고, 샌드박스가 mini-redis-benchmark.exe / mini-rdbms-benchmark.exe를 반복 비교 × 선택 시스템 수만큼만 실행합니다. 조회 반복과 라운드는 C 프로세스 안에서 수행하며, 데이터 생성·삽입·인덱스 구축·조회 목록 생성·워밍업·출력은 측정 구간 밖입니다. 반복 비교마다 시스템 실행 순서를 바꿉니다.

벤치마크 대상

벤치마크 대기 중입니다.

두 계층의 의미와 비교할 때 주의할 점
  • 전체 조회: 각 시스템이 키·ID로 값을 돌려주기까지의 처리입니다. RDBMS는 SQL 처리와 레코드 반환을 포함합니다. 결과 변환 포함 여부와 정확한 범위는 결과의 metadata.full_lookup_scope를 그대로 보여 줍니다.
  • 순수 자료구조 탐색: Redis는 해시 테이블의 키→엔트리/값 탐색, B+ 트리는 ID→CSV 위치(오프셋) 탐색입니다. B+ 트리 쪽은 CSV 읽기·파싱을 제외하므로 반환 대상이 다릅니다. 같은 일을 하는 자료구조 비교로 읽지 마세요. 범위는 metadata.pure_lookup_scope를 따릅니다.
  • scan은 CSV 선형 탐색이라 파일 기반 전체 조회만 측정합니다. 순수 탐색 값은 만들지 않습니다(null).
  • OS 파일 캐시를 비우지 않으므로 cold disk 결과가 아닙니다. 빌드 옵션·시계·저장·flush 조건은 실행 파일이 보고한 metadata로 함께 저장합니다.
  • C 내부 시간, HTTP 실험의 엔진 시간, 브라우저 RTT는 서로 다른 계층입니다. 한 값으로 다른 계층의 성능을 대표하지 않습니다.

6. Redis 버킷 구조 비교 (list vs rbtree, 같은 해시 테이블의 버킷 내부 구조)

같은 키·값·조회 목록·해시 시드·초기 버킷 수로 두 구조를 비교합니다. 데이터는 mini-redis-bucket-benchmark.exe --prepare-only가 만들고, 키에 접두사를 붙이지 않습니다(충돌 조건 보존). 그래서 HTTP 측정은 구조마다 새 전용 Redis 인스턴스에서만 하며 사용자 서버의 데이터는 건드리지 않습니다. C 측정은 구조마다 헬퍼 프로세스 하나로 실행합니다. 라운드마다 구조 순서를 바꿉니다.

비교 구조
측정 계층 (결과는 따로 표시)
키 분포

비교 대기 중입니다.

측정 구간과 해석 시 주의할 점
  • C 전체 삽입: 헬퍼가 보고한 insertion_ms. 삽입마다의 중복 검사와 그 삽입이 일으킨 동기 리해시를 포함합니다. 리해시 시간(rehash_ms)은 이 안에 이미 들어 있으므로 더하지 않습니다. 삽입별 지연은 헬퍼가 삽입마다 시계를 읽은 값이며, 리해시를 일으킨 삽입과 아닌 삽입을 나눠 보입니다.
  • C 조회 구간: 조회 목록 전체를 한 번에 잰 시간(checksum·적중 수 누적 포함, 정확성 검증은 밖). 조회당 시간은 구간 ÷ 조회 수로 계산한 파생값입니다.
  • HTTP 왕복: 샌드박스 Node가 요청을 만들기 직전부터 응답 본문 수신까지. HTTP 파싱·통신·이벤트 루프 대기를 포함하며 순수 엔진 시간이 아닙니다. 브라우저 RTT·프록시 구간과도 다른 계층입니다. engine은 서버가 Server-Timing으로 보낸 store 연산 시간입니다.
  • HTTP 리해시 판정: 각 PUT의 측정이 끝난 뒤 /health의 rehash_count 변화를 읽어 정합니다. 이 조회는 PUT 왕복 합에 넣지 않습니다. 읽지 못하면 “알 수 없음”으로 남깁니다.
  • 준비(데이터 생성·인스턴스 시작·상태 확인), 검증(값·적중·미적중·통계), 정리(인스턴스 중지)는 측정 구간 밖입니다. 성공으로 세는 것은 값·상태가 확인된 요청뿐입니다.
  • 충돌 집중 조건은 헬퍼가 키를 만들 때 확인한 값(초기·최종 용량 집중)과, 측정 뒤 실제 통계의 최대 버킷 크기 = 건수로 따로 확인합니다.
  • 이전 실행 파일(구조 선택 미지원)은 시작하지 못하거나 /health에 구조를 보고하지 않습니다. 이 경우 실험을 멈추고 지원하지 않는다고 표시합니다. 구조를 추정하지 않습니다.

7. 측정 경계와 해석

바깥 구간이 안쪽 구간을 포함합니다: 브라우저 RTT ⊃ 프록시–서버 구간 ⊃ 서버 내부 지표(RDBMS db_exec, Redis Server-Timing). 포함 관계가 있으므로 더하거나 빼서 “순수 서버 시간”을 만들지 않습니다. 프록시–서버 구간도 순수 서버 처리 시간이 아닙니다.

시간 지표의 시작·종료 지점과 포함 범위
지표계층범위

RDBMS와 Redis 비교 시 남는 차이: RDBMS db_exec 시간은 SQL 파싱·검증, CSV 입출력(삽입은 fflush 포함), 결과 JSON 직렬화 콜백을 포함합니다. Redis 저장소 시간에는 이런 작업이 없습니다. 두 값은 같은 범위가 아니므로 “엔진 우열”로 바로 비교하지 마세요.
